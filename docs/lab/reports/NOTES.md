All five Lites pass their self-test, and nothing here needs action before the next build. Every figure in this reading is filled in from the same run as the table below (`NOTES.md` holds placeholders that `--readme-only` fills), so the two can't disagree. In plain words:

- **Lites 3 and 4 run the diagnostics code** (`api diag`), so only they have stack, CPU, Wi-Fi drop, boot, underrun and NVS figures. Lite 4 has it because the code is now in `main`, and the security lane flashed Lite 4 from `main`. Lite 3 runs the same code plus the review fixes (PR #192). Lites 1, 2 and 5 are read from `state` and the self-test, which give heap, PSRAM, RSSI and the power rails; their columns fill in when they next take a `main` image. Uplink and OTA figures are only on Lite 3, because the report runs the 1 MB uplink test only on a board this lane holds.
- **Heap.** Every board reads it the same way (`state`'s byte-addressable internal RAM), and all five are in line: {{min:heap_free|kb}} to {{max:heap_free|kb}} KB free. An earlier version of this page said Lite 3 had twice the heap of the others. That was wrong: its old `diag` also counted IRAM. The lowest free heap since boot is {{min:heap_min|kb1}} KB, on {{argmin:heap_min}}, after only {{argmin:heap_min>uptime_s}} s up. That still works, but it is the tightest figure on the page: if a board ever fails to allocate, start here. The soak on Lite 3 tracks it over hours.
- **Stacks.** The tightest app stack (the task, then the bytes it has never used) is {{Lite 3:stack_tightest}} on Lite 3 and {{Lite 4:stack_tightest}} on Lite 4. `hifi_relay`, which parses JSON, is the one to watch: on the 4 KB stack in `main` it is already that low after {{Lite 4:uptime_s|min}} minutes on Lite 4, and Lite 3 read 708 B on it hours after boot. PR #192 gives it 5 KB, and Lite 3 now has 1.8 to 1.9 KB of it free. `hifi_power` sits just under the 1 KB line the report flags on both. The `ipc0`, `ipc1` and `IDLE` tasks run close to their stack size by design (ESP-IDF sizes them), so they are left out.
- **CPU.** The busiest core was {{Lite 3:cpu_busy_pct}} % busy on Lite 3 and {{Lite 4:cpu_busy_pct}} % on Lite 4, mostly the I2S output and the power monitor, so there is plenty of headroom. A test tone is different: `hifi_tone` takes most of a core while it plays (the soak reads 80 to 100 % on that core), so read CPU only between tones.
- **Wi-Fi.** The boards read {{min:rssi}} to {{max:rssi}} dBm; the weakest is {{argmin:rssi}}. That is still a good signal, but if it ever drops audio, check it first. It is probably placement or its antenna rather than a fault.
- **Uplink and timing.** 1 MB went up Lite 3's bench link at {{Lite 3:echo_kbps|mbit}} Mbit/s. Wi-Fi and the remote link came up {{min:boot_link_ms|s}} to {{max:boot_link_ms|s}} s after boot. Lite 3's last OTA spent {{Lite 3:ota_write_ms|s}} s writing to flash. There have been {{max:underruns}} underruns on either board. The output path held {{min:latency_ms}} to {{max:latency_ms}} ms of audio when read: that is the I2S DMA alone when idle, and the output buffer adds to it while a stream plays.
- **Power.** On all five boards the PD contract holds at 20 V (VBUS {{min:vbus_v}} to {{max:vbus_v}} V). The current each charger offers differs, from {{min:contract_a}} A to {{max:contract_a}} A (the table has each board). That is the charger, not the board, but a 1.5 A (30 W) contract caps the amp's power on a board that has one. The most amp faults on any board is {{max:amp_faults}}. Some boards read PVDD slightly *above* VBUS, by up to {{max:pvdd_over_vbus}} V on {{argmax:pvdd_over_vbus}}. That can't be true in hardware, so it is the tolerance of the two voltage dividers and the ADC (about 1 to 2 %). Treat rail readings as about ±0.3 V, or calibrate each board against a meter if a tighter figure matters.
- **Soak (Lite 3, 2026-11-17).** It ran 7.7 h of a planned 12 (232 cycles), until a power cut at 10:56 EST when Lite 3's USB-C plug shifted. Chart: [lite3-soak-2026-11-17.png](lite3-soak-2026-11-17.png). No tone failed, nothing underran, and the board didn't reboot. Free heap fell once, by about 736 B, after the one Wi-Fi drop early on, then stayed flat for 7 h. The lowest-since-boot figure and every stack stayed flat too. That step is the Wi-Fi reconnect leak the security lane is chasing; the next long soak waits for its fix. The link dropped 9 times (a bench restart is left out). Most of those were the board giving up while the bench still held the link. From hifi-receiver #212, each drop logs why.
- **Uptime** differs only because the boards were restarted at different times, so it doesn't mean anything.
